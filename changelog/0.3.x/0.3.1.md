# 0.3.1 — 2026-07-26

## Changed

- **Corpus count corrected from 19.4M to 14.5M** across every description surface (`package.json`, `server.json`, `manifest.json`, both plugin manifests, `README.md`, `docs/design.md`, `docs/idea.md`, `CITATION.cff`, `Dockerfile`, `AGENTS.md`/`CLAUDE.md`, `src/index.ts` instructions, and `smithsonian-search-objects.tool.ts`'s `@fileoverview` and `description`). The Smithsonian Open Access API's own `/search` with `rows=0` reports 14,490,868 indexed objects, not 19.4M. CC0 media availability is now stated as scoped to the 5,251,899-object subset that carries it, rather than implied across the whole corpus. ([#41](https://github.com/cyanheads/smithsonian-mcp-server/issues/41))

## Fixed

- **`luceneField()` now always quotes and escapes `\` and `"`.** Previously it quoted a value only when it contained a space and never escaped it, so a vocabulary term carrying a literal `"` (e.g. `Early Iron Age, "Tomb Age"`) closed the Lucene phrase early and matched nothing, and a single-token wildcard value (`place: "*"`) was emitted unquoted and matched every record in the field — reporting a term with 124 objects as 12.4M. Affects `smithsonian_search_objects` filters and every `smithsonian_browse_category` mode. ([#42](https://github.com/cyanheads/smithsonian-mcp-server/issues/42))
- **`smithsonian_browse_category`'s `format()` renders `is_cc0` on both branches.** It previously appended a `· CC0` marker only when true, so `content[]` couldn't distinguish `is_cc0: false` from a field the renderer never covered. Now renders `**CC0:** Yes` / `**CC0:** No`, matching the other four tools that render the flag. ([#45](https://github.com/cyanheads/smithsonian-mcp-server/issues/45))

## Dependencies

- `@cyanheads/mcp-ts-core` `^0.10.15` → `^0.10.16`
- `Dockerfile`'s OTEL `bun add` step now passes `--omit=dev --ignore-scripts`, and `.gitignore`'s `data/` entry is now anchored to `/data/` — both template fixes the framework's `init` scaffold doesn't backport to existing projects on upgrade.
