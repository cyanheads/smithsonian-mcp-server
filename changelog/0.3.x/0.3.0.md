# 0.3.0 — 2026-07-26

## Changed

- **`smithsonian_search_objects` `filters.date_decade` renamed to `filters.date`** and no longer gated to the `NNNNs` decade shape — the indexed `date` vocabulary carries 201 terms, of which only 73 are decade-shaped; the old `.regex(/^\d{4}s$/)` gate rejected the other 128 (year ranges like `"500-1500"`, century terms like `"21st century"`, BCE forms like `"-2500"`, `"BCE 1000s"`). **Breaking, and the failure is silent:** neither `filters` schema uses `.strict()`, so Zod v4 drops an unknown `date_decade` key rather than rejecting it — a caller still sending the old field name gets the call succeed with the date filter silently missing, not an error. ([#36](https://github.com/cyanheads/smithsonian-mcp-server/issues/36))
- **`smithsonian_browse_category` `period` mode** drops its `superRefine` decade-shape validation for the same reason — any indexed `date` term is now accepted.
- **`smithsonian_find_related`'s `search_continuation.filters.date_decade` output field renamed to `date`** alongside the input rename, since it's documented as verbatim `smithsonian_search_objects` input. The non-decade-shape fallback that emitted a raw Lucene expression instead of a structured filter is removed — every period now round-trips through `filters.date`. ([#36](https://github.com/cyanheads/smithsonian-mcp-server/issues/36))

## Fixed

- **`smithsonian_search_objects`** — a query-less, filter-less call (`{ query: "" }`) substitutes the upstream match-all term `*` instead of reaching EDAN with an entirely empty `q`, which returned a raw HTTP 400 with no error reason or recovery hint. Filters-present calls with an empty `query` were already unaffected (the filter terms alone produce a non-empty `q`) and remain so. ([#39](https://github.com/cyanheads/smithsonian-mcp-server/issues/39))
