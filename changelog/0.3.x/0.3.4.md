# 0.3.4 — 2026-07-26

## Changed

- **`describeTerm`'s substitute-term search replaces `containsCandidates`'s three fixed cuts with `tightestNeighbors`, a bounded search over every word-boundary-anchored candidate.** Candidates start at each word boundary (advanced past leading punctuation) and may end mid-word, reaching cuts like `Bell UH-1` inside `UH-1H` and `Yank` inside `"Yank"` that the old value / `--`-or-`(`-or-`,`-cut / leading-token ladder could not. A longer candidate replaces a shorter one only when it lists no more terms, so tightness is never traded away for a longer substring that happens to also work. The search is capped at `MAX_NEIGHBOR_PROBES` (48) scans over the cached vocabulary. ([#47](https://github.com/cyanheads/smithsonian-mcp-server/issues/47))
- **A substring listing more than `MAX_NEIGHBOR_TERMS` (800) other terms is discarded**, and the caller falls through to the no-term-route branch instead of being handed a `contains` clause that is functionally the whole field — `culture: "Mzab"` no longer names `M`, which lists 2,936 of the vocabulary's 8,683 terms. ([#48](https://github.com/cyanheads/smithsonian-mcp-server/issues/48))
- **Both tools' recovery-hint wording tracks what the search actually establishes.** A single neighbor now reads "the one other `<field>` term" instead of "one of the 1 other terms"; the dropped-clause branch reads "a bounded search of its fragments found no narrow set of other `<field>` terms to browse" instead of "neither the value nor a leading segment of it" — accurate now that a value can reach that branch after finding a fragment and having it rejected as too broad.
